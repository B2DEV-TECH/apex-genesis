# Native Order Lab control source

This directory contains an isolated APEXlang control application and an additive Oracle request queue. **Native control application 134 is imported and verified only in the explicitly authorized `APXGEN_ORDER_LAB` owner/workspace. Its control UI is enabled for the single approved synthetic operator, with one genuine DRAFT request. The worker remains disabled, without binding or heartbeat; no request is queued and no native evolution run has started.** Its control tables, triggers and package are valid in that owner. Existing applications 120, 121, 130, 131, 132 and 133 are excluded from control-application configuration; their metadata, fixture data and experiment histories were compared before and after installation, import, browser and role verification and remain unchanged.

The template passed genuine offline SQLcl 26.3 / APEXlang 26.2 validation, with zero warnings. That result establishes source acceptance, not authentication, database compilation or runtime behavior. The current portable compiler record and raw output are preserved in `evidence/queued-feasibility-v1/`, with account-specific executable paths omitted. The application reuses the repository's Oracle APEX Accounts login, navigation bar, global page and Universal Theme. Its three authenticated pages are Create, Evolve and Watch. Every input and action starts disabled. Application 134 is protected native infrastructure outside the descendant application pool 130–133; it is not an experiment organism and has no fabricated genetic lineage.

Create records an immutable `GA_ONLY` draft with an explicit single-line label, seed, generation count and application materialization budget. Labels are limited to 120 UTF-8 bytes and reject control characters, including NUL, newline and DEL. The initial capability version is `order-lab-queued-feasibility/1.0`: exactly seed **50000**, **one** challenger generation and **two** application materializations, including its baseline. These values remain visible and read-only in the native form. The SQL and browser contracts reject any other combination, unknown fields, duplicate keys, coerced integers or paid-mode fields. Broader schema/configuration ceilings do not advertise support; `status_json` reports only the implemented capability. Supporting other seeds or larger experiments requires a protocol and worker change plus genuine validation.

Start Evolution changes `DRAFT` to `QUEUED` only when an explicitly configured worker has reported a heartbeat within 60 seconds. Queueing does not create a run, generate a descendant or import an application. Watch displays the queue state separately from the linked Oracle run and its actual organisms and phase events. An unmeasured score remains `null`; the interface says “not evaluated”. Fitness remains the bounded engineering proxy `order-lab-task-proxy/2.0.0`.

`sql/010_control_queue.sql` creates disabled, unbound configuration, an empty explicit role allowlist, immutable bounded requests and append-only request audit. `sql/apxgen_app_control.sql` checks current authenticated APEX application, workspace, parsing owner, principal and explicit `READER` or `OPERATOR` membership. Readers can observe; operators can create, enqueue and cancel requests before claim. Configuration and role administration have no browser endpoint. Callback errors contain no database diagnostics or connection identities. Browser rendering uses text nodes.

The direct-owner worker API is separate from the APEX callback. It requires no active APEX session and the exact enabled worker binding. Claims receive a private token and a 30–300 second lease. A worker must commit the claim before any external operation, renew it before expiration, and commit each renewal. Expired claims become permanent `UNCERTAIN` outcomes; they are never automatically requeued. A terminal or uncertain request cannot be adopted or rewritten.

`validate_payload` provides the same pure Oracle request grammar for independent contract checks while control remains disabled. `create_draft`, queue admission and worker claim each enforce the fixed feasibility capability. `worker_attach_run` accepts one fresh, unexecuted Oracle baseline run whose label, seed, generation count, materialization budget and GA_ONLY fitness contract match the claimed request. It rejects a historical run, an executed candidate, changed budgets and a second link. The worker must commit the link before materialization. `worker_finish` derives completion or failure from the linked Oracle terminal run state. These wrappers do not bypass the existing compiler/import ledger, slot ownership, task evaluator or Oracle decision engine. They never call a provider or reserve an application ID.
