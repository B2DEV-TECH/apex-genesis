# Living Applications design (implementation in progress)

The APEX Genesis 0.3 master brief governs this extension. Oracle remains the
evolution and fitness authority. Existing dashboard genomes, scores, autonomous
runs, AI accounting, public archives and applications remain independent.

## First bounded vocabulary

Application genome 2.0 describes Genesis Order Lab and its three fixed tasks:
`locateOrder`, `filterOrders`, `updateOrder`. Its fixed data source is
`GENESIS_ORDERS_SAFE_V`. Six traits select predefined components and arrangement:
`report`: classicReport/interactiveReport; `edit`: page/modal;
`filters`: above/beside; `summary`: before/after; `navigation`: side/top;
`density`: comfortable/compact. These are Genesis trait names, not APEXlang syntax.
Unknown keys, executable text, URLs and changes to tasks/data source are rejected.
Only template mappings that pass the installed compiler may be materialized.

An additive PL/SQL package owns deterministic generation, mutation, crossover,
strict canonicalization and proposal validation. Another owns the versioned
task-proxy score. Neither changes historical packages or their fitness definition.

## Materialization and evidence

The worker requires an owner-configured development sandbox: exact workspace,
parsing schema, allowed disposable application IDs and explicit fixture permission.
No destination is inferred from existing privileges. Application 120 and 121 are
existing applications and are excluded from any implicit allocation. Slot ownership
must be recorded before reuse; naming patterns never prove ownership.

Genome creation, definition generation, compiler validation, import, runtime check,
functional testing and Oracle selection are separate observations. Import process
success alone does not prove existence or runtime correctness. No generated code
is accepted from genomes or model responses. Trusted templates supply fixed SQL,
authorization and parameterized Order Lab procedures. Per-evaluation data is reset
through a trusted fixture API and isolated by an owned application slot.

The public exhibition consumes immutable, hash-verified recorded evidence. It
shows an explicit empty state until genuine materialized application records exist.
Screenshots never substitute for import/runtime/task verification. Public artifacts
exclude credentials, sessions, internal endpoints and authentication recordings.

## Research and release gates

Task-based fitness 2.0 is separate from dashboard fitness. Its proposed weights
are 35/25/20/10/10 for task effort, navigation, accessibility/responsiveness,
performance and simplicity. Exact normalizations and protocol must be frozen
before running a cohort. Automated effort remains an engineering proxy, without
claims about human satisfaction or aesthetic superiority.

GA_ONLY needs no provider. GA_HAIKU requires a fresh per-run authorization and
integration with the existing ledger; no parallel ledger or historical-budget reuse.
Until that integration is verified, application mode must refuse paid execution.

The target remains v0.3.0-alpha.1. No release tag, follow-up findings article or
demonstration video is justified until real application acceptance criteria pass.
Missing sandbox authorization or tooling is recorded as an incomplete gate.
